# v0.2 单项目交付知识助手

> 本知识包中的公司、业务、日期和事件均为虚构演示内容，仅用于 RAG 系统开发、评估与公开展示，不对应任何真实企业、客户或项目。

知源 v0.2 使用“悦享咖啡会员小程序2.0升级项目”作为单项目交付知识助手的验证场景。它面向新加入项目的成员、项目经理、产品、设计、开发、测试、交付和客户支持人员，回答项目背景、范围、里程碑、会议决定、需求变更、风险与验收标准等问题。

本目录公开的是可复现的虚构知识包和固定评估集，不包含 Dify API Key、模型供应商凭据、本地 Dify 数据库或原始评估结果。

## 目录内容

- `project-blueprint.md`：项目唯一事实来源，用于约束文档与测试题，**不上传到 Dify**；
- `source/`：9份已审核、可上传到 Dify 的正式 Markdown；
- `evaluation/project-delivery-test-cases.json`：30个固定槽位，其中启用10道 ANSWER 和5道 REFUSE；
- `evaluation/results/`：本地原始结果目录，由 Git 忽略，不进入仓库。

上传知识库时只使用 `source/` 中的9份文档。不得上传项目蓝图或评估 JSON，以免测试参考答案、边界说明或重复事实污染检索结果。

## v0.2 最终冻结配置

以下配置是当前知识包经过固定测试与单变量对照后采用的最终基线。它不是对其他知识库的通用推荐。

| 层级 | 最终配置 |
| --- | --- |
| 知识库资料 | `source/` 中9份已审核 Markdown |
| 父级上下文 | 全文 |
| 子分隔符 | 单换行 `\n` |
| 子 Chunk 最大长度 | 512 |
| 索引方式 | 高质量索引 |
| Embedding | `text-embedding-v4` |
| Knowledge Base 检索 | 向量/语义检索 |
| Knowledge Base Top K | 10 |
| Knowledge Base Score Threshold | 0.5 |
| Knowledge Base Rerank | 关闭 |
| Chatflow Top K | 4 |
| Chatflow Score Threshold | 0.5 |
| Semantic Weight | 1.0 |
| Keyword Weight | 0 |
| Chatflow Rerank | 关闭 |
| LLM | 当前已发布 v0.2 Chatflow 中经人工确认的模型配置 |
| Prompt | 当前人工确认版本 |

Prompt只约束“历史规则与当前规则冲突时，以检索到的当前有效版本为准”，不直接写入四条优惠券业务规则。业务答案必须来自知识库检索，不能通过Prompt预先提供。

## 为什么选择全文父上下文

父子分段中，子 Chunk 负责找到与问题最相近的文本；命中后返回的父上下文负责给模型提供足够完整的证据。本轮只改变父上下文组织方式，保留其他配置和固定测试题，用三阶段实验观察改善与回归。

### Baseline：空行切分的段落父块

- 父级上下文：段落；
- 父分隔符：空行；
- 正式评估：10/15严格通过；
- ANSWER：5/10；
- REFUSE人工复核：5/5；
- 平均响应时间：约1.72秒。

主要问题是标题、列表、风险描述、影响和性能指标可能被拆入不同父片段。命中正确文件，并不代表真正支持答案的证据进入Chatflow最终上下文。

### exp01：按 Markdown H2 边界组织父块

- 父级上下文仍为段落；
- 父分隔符调整为 Markdown 二级标题边界；
- 只进行检索诊断，没有把它作为正式最终评估配置。

诊断结果：

- `project-answer-006` 的完整优惠券规则由Rank 8提升到Rank 5；
- `project-answer-009` 的风险父段完整性得到改善；
- `project-answer-010` 的完整性能指标从Top 10外提升到Rank 1；
- `project-answer-002` 仍受到同一H2下多个H3事实组分散的影响。

章节级父段明显改善了结构完整性，但没有稳定解决所有多事实组问题。

### exp02：子Chunk检索，返回全文父上下文

- 父级上下文改为全文；
- 子Chunk仍负责精准检索；
- 9份文档平均约1,256个字符；
- 最长文档约1,698个字符。

第一次Baseline失败的5道ANSWER题在原始检索诊断中都能获得完整答案证据。随后只运行这5题的小规模LLM验证，其中002、005、009、010恢复严格通过，006仍失败，恢复结果为4/5。

## exp02完整15题正式评估

第二轮保持配置、Prompt、知识库文档、测试题和参考答案不变，连续运行15道启用题。原始JSON与Markdown包含完整回答和检索内容，只保存在本地忽略目录中；仓库公开以下人工严格复核结论。

| 指标 | exp02结果 |
| --- | ---: |
| 请求成功 | 15/15 |
| 总严格通过 | **13/15** |
| ANSWER严格通过 | **8/10** |
| ANSWER事实正确 | **8/10** |
| REFUSE人工严格通过 | **5/5** |
| 至少一份预期文件命中 | 10/10 |
| 多文档预期文件完整命中 | 3/4 |

### Baseline与exp02对照

| 指标 | Baseline | exp02 | 变化 |
| --- | ---: | ---: | ---: |
| 总严格通过 | 10/15 | 13/15 | +3 |
| ANSWER严格通过 | 5/10 | 8/10 | +3 |
| REFUSE人工严格通过 | 5/5 | 5/5 | 不变 |

4道原失败题恢复，1道原通过题回归，净收益为 `4 - 1 = +3`。本轮没有观察到可以明确归因于全文冗余的失败。

## 两道未通过题

### project-answer-006：当前真实RAG限制

`scope-and-requirements.md` 没有进入Chatflow最终上下文，模型因而没有取得四条当前优惠券规则。模型正确选择不凭空补全，只说明当前规则由该文档维护。

这是多文档检索和最终上下文覆盖的边界问题。v0.2不再为这一题继续调整参数，并将其作为已知限制保留。

### project-answer-003：一次孤立的年份转写错误

正确文档已经完整进入上下文，所有引用均为2032年，四条业务规则也回答正确；但一次正式运行把“2032年9月22日”误写为“2022年9月22日”。

当前没有证据表明该错误是稳定可复现的RAG配置缺陷，因此它记录为实验观察，不列为系统性已知限制，也不通过重跑覆盖原始正式结果。

## REFUSE自动评分器说明

5道REFUSE题经人工严格复核全部通过。模型引用了“未提供”“未定义”“没有具体日期”“待后续确认”等真实边界证据，并据此拒绝编造。

现有自动拒答检测器只匹配有限的固定短语，因此本轮自动结果为0/5。这是evaluation scorer的短语覆盖问题，不代表RAG实际拒答能力为0/5。

后续可以在不重新调用模型、不改写历史结果的前提下：

1. 为上述合理表达补充拒答标记；
2. 用保存的回答和现有单元测试验证检测规则；
3. 在报告中继续同时保留“自动检测”和“人工严格复核”两项结果。

本次冻结不修改评分器，也不回写原始评估历史。

## 适用边界

exp02是针对当前数据形态作出的工程决策：9份知识文档都是短、结构化Markdown，平均约1,256个字符，最长约1,698个字符。在这组固定测试中，全文父上下文改善了证据完整性，且没有观察到明显的上下文冗余型失败。

这不表示全文父上下文普遍优于章节级Chunk，也不表示该配置适用于任意企业PDF或大型知识库。文档数量增加或单篇变长后，全文上下文可能引入更多无关信息、延迟和模型注意力竞争。

未来长文档更合理的候选方向包括：

- 按业务章节建立语义父块；
- 在入库前进行文档结构预处理；
- 对PDF标题、表格、图片和跨页内容完成解析后再进入RAG。

这些仅是后续方向，v0.2没有实现PDF预处理助手。

## 测试集格式检查

下面的命令只检查30个槽位和15道启用题的JSON格式，不调用Dify或模型：

```powershell
npm.cmd run rag:evaluate:check -- --dataset knowledge-packs/project-delivery-demo/evaluation/project-delivery-test-cases.json
```

完整评估会产生真实模型调用。运行时应显式指定企业测试集和独立结果目录，避免覆盖v0.1历史：

```powershell
npm.cmd run rag:evaluate -- `
  --dataset knowledge-packs/project-delivery-demo/evaluation/project-delivery-test-cases.json `
  --output-dir knowledge-packs/project-delivery-demo/evaluation/results/local-run
```

`evaluation/results/` 中的原始结果由Git忽略，不应提交。
