# 知源项目决策记录

这份文档记录 v0.1 阶段已经做出的重要选择。它不是“永远不变的答案”，而是帮助项目复盘：当证据变化时，可以知道为什么需要调整。

## 1. 使用 RAG，而不是让大模型直接回答课程问题

- **决策是什么：** AI 回答前先从课程知识库检索资料，再依据检索结果作答；找不到依据时拒答。
- **为什么这样做：** 知源的核心目标不是开放聊天，而是让回答能回到课程资料，并让用户看到来源。直接回答无法稳定证明内容来自当前课程资料。
- **考虑过哪些替代方案：** 直接让通用大模型回答；把全部资料一次性放入提示词；对模型进行微调。
- **当前证据是什么：** 本地链路已经能返回 Dify 的真实检索片段，并已验证有资料回答和无资料拒答。30 题评估尚未完成，因此准确度和成本仍待评估。
- **是否已经最终确定：** v0.1 阶段已确定，长期方案未最终确定。
- **后续什么情况可能改变：** 如果固定评估显示检索长期无法覆盖核心问题，或资料规模、成本和延迟出现明显瓶颈，需要重新比较其他方案。

## 2. 当前选择 Dify，而不是直接使用 LangChain 开发

- **决策是什么：** v0.1 使用本地 Dify Chatflow 管理知识检索和回答流程，网站通过 API 调用它。
- **为什么这样做：** 当前 Dify 已成功本地部署、配置并发布 Chatflow，检索、拒答、流式回答和真实引用链路均已跑通；继续使用它能保留已经验证的成果。
- **考虑过哪些替代方案：** 使用 LangChain 或其他代码框架自行编排检索和生成；直接调用模型与向量数据库。
- **当前证据是什么：** Dify 方案已有可运行的 Chatflow DSL 和真实冒烟测试。LangChain 方案尚未在本项目中做同等测试，因此不能断言它更差或更贵。
- **是否已经最终确定：** 仅对 v0.1 阶段确定。
- **后续什么情况可能改变：** 如果需要的检索控制、自动化测试、调试能力或部署方式超出 Dify 的可控范围，再用同一评估集比较代码化方案。

## 3. 使用 Next.js 服务端代理 Dify

- **决策是什么：** 浏览器只请求知源的 `/api/chat`，由 Next.js 服务端再调用 Dify。
- **为什么这样做：** 这样可以把 Dify 地址、鉴权和响应转换集中在服务端，并统一把 Dify 的流式事件转换成页面需要的格式。
- **考虑过哪些替代方案：** 浏览器直接调用 Dify；另建一个独立后端服务。
- **当前证据是什么：** `/assistant` 已通过该链路完成 SSE 流式回答和真实引用验证。独立后端是否更适合公开部署仍待评估。
- **是否已经最终确定：** v0.1 已确定。
- **后续什么情况可能改变：** 当并发、限流、审计或后台任务超出 Next.js 服务端接口的承载范围时，再评估拆分后端。

## 4. API Key 不进入浏览器

- **决策是什么：** Dify API Key 只保存在服务端环境变量中，不写入前端代码、页面响应或 Git。
- **为什么这样做：** 浏览器中的代码和网络请求可被使用者查看；一旦 Key 暴露，别人可能冒用接口、产生费用或访问不该访问的能力。
- **考虑过哪些替代方案：** 把 Key 写进前端环境变量；让每位使用者自己填写 Key。两者都不符合当前无需登录的产品范围。
- **当前证据是什么：** 真实 Key 目前位于被 Git 忽略的 `.env.local`；提交候选扫描未发现静态 Bearer 值或疑似真实 Key。
- **是否已经最终确定：** 安全原则已最终确定。
- **后续什么情况可能改变：** Key 的具体保存介质可能改为部署平台的密钥管理，但“不得发给浏览器”的原则不变。

## 5. 使用 SSE 流式输出

- **决策是什么：** 服务端与页面使用 SSE，收到回答增量后立即显示，不等待全文生成完毕。
- **为什么这样做：** AI 回答可能需要数秒；逐步显示能让用户知道请求仍在进行，并能区分正常生成、断流和服务错误。
- **考虑过哪些替代方案：** 等完整答案后一次返回；使用 WebSocket。
- **当前证据是什么：** 当前页面已验证 `answer.delta` 增量显示、完成事件、断流与错误处理。SSE 与 WebSocket 在公开并发下的差异待评估。
- **是否已经最终确定：** v0.1 已确定。
- **后续什么情况可能改变：** 如果未来出现双向实时协作等需求，再评估 WebSocket；当前没有这类需求。

## 6. 只展示真实 `retriever_resources`

- **决策是什么：** 引用由 Next.js 服务端读取 Dify 返回的检索资源并构造，不能让大模型在答案中自行生成引用对象。
- **为什么这样做：** 模型写出的文件名、片段或编号可能并未真正被检索。保留真实字段才能检查命中文件、片段、分数与原文。
- **考虑过哪些替代方案：** 让模型按 JSON 格式输出引用；根据答案文字猜测来源；前端拼接固定来源。
- **当前证据是什么：** 现有页面和冒烟测试已保存 `document_id`、`segment_id`、`document_name`、`score` 和 `content`。
- **是否已经最终确定：** v0.1 的引用原则已最终确定。
- **后续什么情况可能改变：** 可以增加站内资料映射或更友好的显示，但底层仍应保留真实检索字段。

## 7. 资料不足时明确拒答

- **决策是什么：** 知识库没有足够依据时，说明资料不足，不编造课程规定、考试内容或标准答案。
- **为什么这样做：** 知源强调可核查的课程资料；不确定时继续作答会破坏引用可靠性，也可能误导学习。
- **考虑过哪些替代方案：** 使用通用知识补充答案；自动取消章节限制扩大检索；给出无来源的“可能答案”。
- **当前证据是什么：** 已完成一条无资料拒答链路验证；5 道不同类型的拒答题仍需作为首批基线进一步验证。
- **是否已经最终确定：** 原则已确定，拒答措辞和规则仍待评估。
- **后续什么情况可能改变：** 如果产品未来允许明确区分“课程资料回答”和“通用补充”，可重新设计界面和规则，但两类依据必须清楚分开。

## 8. 建立固定 RAG 评估集

- **决策是什么：** 使用版本化的固定题目，记录期望文档、真实检索、答案、拒答和延迟；先人工复核，不用另一个大模型打分。
- **为什么这样做：** 调整检索或提示词后，需要用同一批问题比较变化，避免只凭几个顺手例子判断效果。
- **考虑过哪些替代方案：** 每次临时提问；只看最终回答；用另一个大模型自动评分。
- **当前证据是什么：** 已有批量脚本、JSON 结果和 Markdown 人工报告框架；目前只有一条真实冒烟记录，完整基线尚待本轮运行。
- **是否已经最终确定：** 方法已确定，题目和评分细则将持续完善。
- **后续什么情况可能改变：** 人工样本足够多且评分标准稳定后，可评估增加自动辅助评分，但不能替代可追溯的人工复核。

## 9. 当前不加入登录、社区和用户上传

- **决策是什么：** v0.1 只验证资料浏览、搜索和带真实引用的 AI 问答，不加入账号、社区、支付或用户上传。
- **为什么这样做：** 当前首要风险是检索是否命中、回答是否忠实、引用是否正确。额外功能会引入权限、隐私、审核和存储问题，不能证明核心 RAG 更可靠。
- **考虑过哪些替代方案：** 首版同时实现完整平台；先做账号体系；允许同学上传资料。
- **当前证据是什么：** 项目由一人维护、仅少量同学计划测试，且第一阶段目标明确限定为可演示原型。功能需求是否会在测试后改变，待用户反馈。
- **是否已经最终确定：** v0.1 范围已确定。
- **后续什么情况可能改变：** 核心评估达到可接受水平、资料版权和审核流程明确后，再按真实需求逐项加入。

## 10. 暂时不直接公开部署

- **决策是什么：** 先建立安全 Git 基线和 RAG 评估基线，再决定公开部署。
- **为什么这样做：** 本地成功不等于公开环境安全稳定；公开前仍需确认密钥管理、匿名限流、日志隐私、课程资料授权、部署配置和故障处理。
- **考虑过哪些替代方案：** 立即购买服务器并开放访问；只做局域网演示。
- **当前证据是什么：** 本地核心链路已跑通，但当前没有域名和服务器，公开环境的并发、成本和隐私策略均未验证。
- **是否已经最终确定：** “现在不部署”已确定；最终部署平台和时间待评估。
- **后续什么情况可能改变：** 完成首轮评估、确认资料可公开范围、补齐发布安全项并获得小范围测试反馈后，再做部署决策。
